# ADR 0017 — A real lint gate, and CI that runs it

**Status:** accepted · targets v1.16.1 (no user-facing change)

## Context

`npm run lint` had never worked on this repository. At some point `expo lint`
scaffolded an `eslint.config.js` and the install never followed, so neither
`eslint` nor `eslint-config-expo` was in `package.json`. The config file sat
**untracked** in the working tree for months, the script failed on every
invocation, and the failure was quietly treated as "lint is broken here" rather
than as a missing dependency.

There was also no `.github/` at all and no `typecheck` script. So the only thing
checking any branch was a human remembering to type `npx tsc --noEmit`, and the
only record that it had been done was a sentence in a PR body.

This mattered more than usual right at this moment: three large, mechanical
refactors were queued behind it (a shared `Avatar` across nine files, an
accessibility pass over every control, a query-key migration touching 27 files).
Those are exactly the changes where a machine catches what review misses.

## Decision

**Install the linter, turn it on at zero warnings, and put both checks in CI.**

- `eslint` 9 + `eslint-config-expo` 56, installed with **`expo install`** rather
  than `npm i`, so versions resolve against SDK 56 instead of latest. The
  scaffolded `eslint.config.js` is committed as-is, plus two ignores:
  - `.expo/*` — generated by expo-router, and carries its own directives.
  - `supabase/functions/*` — **Deno, not Node.** `jsr:@supabase/supabase-js@2`
    is unresolvable to the Node resolver, and `tsconfig.json` already excludes
    these for the same reason. Type-checking the edge functions is a separate
    job for `deno check`, deliberately not folded in here.
- Scripts: `typecheck` (`tsc --noEmit`) and `lint:ci` (`expo lint
  --max-warnings 0`). Plain `lint` stays as it was, for iterating locally.
- **One** GitHub Actions job on push and PR: checkout → setup-node 22 (npm
  cache) → `npm ci` → regenerate `expo-env.d.ts` → `typecheck` → `lint:ci`.
  Nothing else. There is no test suite to run, and `expo export` in CI is a slow
  way to learn what `tsc` already said.

### The generated file CI doesn't have

`expo-env.d.ts` is **gitignored by Expo's own template** — the file says so in
its own body — and it is what references `expo/types`, which supplies the
ambient declarations for CSS modules among other things. Without it `tsc` fails
in a fresh checkout on two files nobody touched, while passing on every
developer's machine. The first CI run failed exactly there.

The workflow regenerates it with `npx expo customize tsconfig.json` — the
lightest Expo command that runs the TypeScript setup — rather than hardcoding
today's three lines, so it stays correct across SDK bumps. That command also
rewrites `tsconfig.json`; it is byte-identical today, and a
`git diff --exit-code tsconfig.json` guard immediately after means a future SDK
that changes it fails the job instead of silently type-checking a different
config than the one in the repository.

### The suppression policy

The first working run surfaced **29 problems (19 errors, 10 warnings)**. It is
now 0/0. Six were fixed outright: four unused imports/vars, and two dependency
arrays — including `range-slider`, which now destructures its two ends up front
so the effect depends on the numbers rather than on a fresh array every render.

The rest are **suppressed per site, each with a written reason**. Three rules
account for all of them, and all three are new React-Compiler-era rules that
this codebase predates:

| rule | sites | why it stays |
|---|---|---|
| `react-hooks/refs` | `range-slider`, `rating-bar`, `library-filter-sheet`, `explore` | a `Gesture.Pan()` builder is constructed during render, but its callbacks only ever run from the gesture — which is exactly when reading `.current` is correct. These refs are mailboxes for a gesture, not render state. |
| `react-hooks/immutability` | `press-scale` | assigning `sharedValue.value` **is** Reanimated's interface, and both writes are in press handlers. |
| `react-hooks/set-state-in-effect` | 9 | seeding local optimistic state from a query or a prop. |

That last row is the one that deserves the honest version: **the rule is right
in general.** Every one of the nine is a live optimistic control — the follow
button, the review-thread like counts, the movie/TV watch bars, the library
filter sheet's draft, the range slider's thumbs. The React-recommended fixes
(derive during render against a previous-value state, or reset via `key`) are
genuine behavioural rewrites of UI that deliberately moves before the server
answers. Doing nine of those inside the PR that first turns the linter on, with
no test suite and no device pass, is how you ship a bug.

Two rules of engagement, so the gate stays worth something:

1. **No blanket or file-level disables, and no rule turned off in the config.**
   A *new* violation of any of these still fails CI.
2. Every disable carries a `--` reason on the directive or a comment above it.

A directive's placement is fiddly: a multi-line block comment applies to the
line after the comment ends, not to the line the reader thinks it points at, so
suppressing a `setState` several lines inside an effect wants a
`disable`/`enable` pair around the effect rather than a `disable-next-line`.

## Consequences

- **The lockfile moves.** That is why this was deferred repeatedly and why it
  is its own PR: `npm ci` in CI is only meaningful if `package-lock.json` is
  the thing being validated.
- **Nineteen suppressions is a lot to carry**, and they are a standing invitation
  to be read as decoration. The nine `set-state-in-effect` ones are tracked as a
  real follow-up, to be done as its own PR with a device pass behind it.
- Every branch from here on gets typecheck + lint automatically, so a PR body
  claiming "tsc clean" is now checkable rather than trusted.
- Deno type-checking for the two edge functions remains uncovered by anything.
